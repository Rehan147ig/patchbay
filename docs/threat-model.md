# Patchbay - Threat Model

Scope: the local-development MVP. Threats below are ordered by relevance to the MVP; each has a
concrete mitigation implemented (or, where noted, a documented production requirement).

## Threat inventory

| #   | Threat                                                                             | Impact                                             | MVP mitigation                                                                                                                                                                                                                                   | Residual risk / production requirement                                                   |
| --- | ---------------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| T1  | GitHub token exposure (in browser, logs, or AI context)                            | Full repo access                                   | Tokens server-side only; short-lived installation tokens (App JWT → installation access token) never sent to client; redaction strips secrets from logs/audit/AI context; UI never renders token material                                        | Production: secret manager, token rotation/revocation UI, audit of token use             |
| T2  | Untrusted repository code (fixtures or connected repos) executed during validation | Arbitrary code execution                           | Validation commands come from fixed allowlist only; commands never built from repo content; timeouts; bounded output; sandbox works on a disposable copy of the repo in a temp workspace                                                         | Production: containerized sandbox with kernel isolation, resource limits, egress control |
| T3  | Prompt injection via changelogs/docs/code comments fed to the AI provider          | Model steered to emit malicious plans/patches      | AI output is advisory only; parsed with Zod; never executes commands; patches require deterministic rule match; AI-labeled outputs cannot bypass policy; context is bounded and redacted                                                         | Production: stronger sanitization, output filters, human review on all AI patches        |
| T4  | Malicious patches (from rules or AI)                                               | Bad code merged                                    | Patches only generated by deterministic rules with exact AST preconditions; re-parse validation; validation must pass; draft PR only; approval for high-risk tags                                                                                | Production: signed patches, review required, CI gating                                   |
| T5  | Arbitrary command execution via parameter injection                                | RCE                                                | sandbox-runner rejects any command outside allowlist (unit-tested); args parsed, not shell-joined except through fixed templates; no env secrets passed to commands                                                                              | Production: sandboxed process isolation                                                  |
| T6  | Tenant isolation failure                                                           | Cross-tenant data leak                             | MVP is single-org by design; all queries scoped by organizationId; policy entities carry organizationId; seed data isolated                                                                                                                      | Production: enforced multi-tenancy, row-level security review                            |
| T7  | Sensitive code excerpts sent to AI                                                 | Secret leakage to model vendor                     | Redaction helper applied before context assembly; excerpt length bounded; AI_PROVIDER=mock default means no network egress by default                                                                                                            | Production: allow-listed providers, DLP review of prompts                                |
| T8  | Audit-log tampering                                                                | Loss of accountability                             | Application-level append-only: no update/delete code paths for AuditEvent; before/after JSON stored per event; UI read-only                                                                                                                      | Production: append-only store (WORM), DB permissions, tamper detection                   |
| T9  | Approval bypass                                                                    | Unsafe changes merged                              | Approval decision stored as Approval row tied to remediationPlanId + user; policy engine re-evaluates every PR creation with fresh DB state; block decisions audited                                                                             | Production: multi-party approval, MFA, separation of duties                              |
| T10 | SSRF via vendor URL ingestion                                                      | Internal network probing                           | MVP never auto-fetches arbitrary URLs; change ingestion is manual/pasted content; `sourceUrl` is stored as data only, never fetched                                                                                                              | Production: URL allowlist, fetch sandbox, no automatic link following                    |
| T11 | Session fixation/hijacking (dev auth)                                              | Account takeover (demo)                            | Signed HttpOnly cookie, expiry; demo user only; fail-closed in production (no default secret, no fallback password, disabled unless GitHub OAuth configured); login rate-limited                                                                 | Production: real identity provider                                                       |
| T12 | Command output leaks secrets                                                       | Info disclosure                                    | stdout/stderr bounded and sanitized via redaction helper before storage/UI                                                                                                                                                                       | Production: secret scanning on output                                                    |
| T13 | Validation tool poisoning (repo scripts override allowlisted scripts)              | Malicious script execution during `pnpm lint` etc. | Fixture repos are static and reviewed; commands run in disposable workspaces; document that repo scripts run as-is is a known limitation of allowlisting script names                                                                            | Production: run scripts in hermetic containers; pinned toolchain                         |
| T14 | Webhook forgery / replay (GitHub App)                                              | Fake PR status, installation tampering             | HMAC `x-hub-signature-256` verification; deliveries deduplicated by `x-github-delivery` (unique WebhookDelivery row); webhooks never create tenant bindings (callback-bound only); PR status updates are monotonic (no closed/merged regression) | Production: webhook rotation, payload schema versioning                                  |

## Data classification

- **Never stored**: real production credentials, GitHub tokens in plaintext, real secrets.
- **Stored with care**: code excerpts (bounded, sanitized), validation stdout/stderr (bounded,
  redacted), OpenAPI documents (user-supplied).
- **Audit events**: always redacted via `redactSecrets` before persist.

## Trust boundaries

1. Browser ↔ API: dev session cookie (T11); Zod validation on all inputs; role checks.
2. API ↔ engines: pure functions; no shell execution from this layer.
3. Engine ↔ host: sandbox-runner is the only path to `child_process`; allowlist enforced.
4. Engine ↔ AI provider: single narrow interface, Zod-validated return, redacted context (T3, T7).
5. App ↔ git provider: local provider operates on temp copies; GitHub App path uses short-lived
   installation tokens (T1); webhook inbound is HMAC-verified and deduplicated (T14).
6. Dev auth: signed cookie fails closed in production (no default secret, no fallback password,
   disabled unless GitHub OAuth is configured); login rate-limited (429).

## Explicit statement (shown in UI and README)

> The bundled validation sandbox and dev authentication are local-development tools, not
> hardened multi-tenant infrastructure. Do not run untrusted repositories against them in a
> shared environment.
